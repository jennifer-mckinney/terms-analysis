# ADR 0002: The weekly wiring audit may send repository source to the Message Batches API

- **Status:** Accepted (the owner's merge of PR #268 is the acceptance; decision card #267, option a)
- **Date:** 2026-10-09
- **Decided by:** owner, by merging PR #268 (#267)
- **Governs:** `.claude/CLAUDE.md` hard requirements HR1 (open source only), HR2 (no investor-lawsuit vendors), HR3 (IRP Grade A or higher), HR4 (local-only data, no external API calls) and HR6 (no OpenAI, local-only LLM inference), as scoped by ADR 0001, plus their restatements in `.claude/library/LIB-PRINCIPLES.md` P5 and `.claude/library/LIB-STACK.md` S1
- **Companion:** legal-corpus-ingester ADR-016 records the same decision for that repo's constraints C3, C4 and C7
- **Supersedes:** nothing. ADR 0001 stays in force; its last consequence ("Other development-time tools are not exempted by this ADR. Each one needs its own decision.") is what this ADR answers for one tool.

## Context

Card #224 adds a weekly, GitHub-hosted audit that asks a Claude model whether each module in this repository is actually wired: entry points with no caller, public functions nothing imports, tests that skip themselves, workflows that never run. Three such silent failures were found by hand on 2026-10-09 (invalid ingester workflow YAML, a `refresh` no-op, review-gate edge cases). Reviews catch diffs; this audit looks for absences.

The audit uses the Anthropic Message Batches API (`POST /v1/messages/batches`), not `claude-code-action`, so ADR 0001's exemption does not cover it. Read literally, HR1-HR4 and HR6 would bar it for the same reasons they would have barred the CI review jobs: a VC-funded LLM vendor, an external API call, LLM inference that is not local.

Design gate, threat model and API research are summarised on issues #224 and #267, which are the citable record. The working notes behind them are untracked evidence files in the lead's checkout and are not part of this repository.

What the threat model concluded, in short: both repositories are public, so run logs, artifacts and filed issues are world-readable; the controls that make that acceptable are that only allowlisted, leak-scanned source leaves the runner (condition 1), that model output never runs as code or shell and is schema-validated before it reaches an issue (condition 7), and that a run can never report success without the canary finding (condition 6). An attacker who controls repository source can at most waste the budget ceiling or cause a loud failure.

## Decision

The weekly wiring audit is development-time tooling and is exempt from HR1, HR2, HR3, HR4 and HR6 on the same footing as the CI review jobs in ADR 0001. HR4 is scoped the same way: this repository's own tracked source may be sent to the Claude API for the audit; user documents, analysis results and legal-KB data never are.

## Conditions

The exemption holds only while all of these are true. If any one stops being true, the exemption lapses and HR1-HR4 and HR6 apply in full.

1. **Source only, allowlisted.** The inventory builder enumerates files with `git ls-files` (never a directory walk) filtered by the configured module globs, then removes every path matching the denylist (`data/**`, `.env*`, `docs/evidence/**`, `.git/**`, virtualenvs, databases, VCR cassettes and recorded fixtures) and every path or line matching `.claude/governance/personal-path-patterns.txt`. Test files stay eligible: the audit's job includes finding tests that skip themselves, and each module prompt carries that module's tests. Every candidate is scanned with `scripts/governance/leak_scan.py` against `.claude/governance/evidence-leak-regex.txt` before any API request, token counting included; "passes" means exit code 1 together with the `CLEAN <n>` sentinel on stdout (that script's clean signal), and any other result, including exit 2, is a refusal. The scanner matches local machine paths, not secrets; the repository is public, so that is the exposure it guards. A golden test pins the exact file list for a known checkout.
2. **GitHub-hosted runners, trusted triggers only.** Both workflows run on `ubuntu-latest`. The ingester copy never runs on the self-hosted runner, where the corpus and secrets share a machine. The workflows trigger only on `schedule` and `workflow_dispatch`; never `pull_request`, `pull_request_target`, `workflow_run`, `issue_comment` or `push`. Because a dispatch on any branch runs that branch's copy of the workflow, the restriction to the default branch is enforced outside the file: the key is an environment secret whose deployment-branch policy allows only the default branch, both jobs declare that `environment:`, and each job carries `if: github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`. A test asserts the `runs-on` value, the trigger set, the `environment:` key and the ref guard.
3. **SHA-pinned actions, least privilege.** Every `uses:` is pinned to a full commit SHA. The submit job has `contents: read`; the collect job has `contents: read`, `actions: read` and `issues: write` and nothing else. No step runs model output through a shell.
4. **Dedicated credential with its own cap.** The workflows use a dedicated Console workspace and key (`WIRING_AUDIT_API_KEY`), stored as the environment secret named in condition 2, with a workspace spend limit set in the Console, so a budget bug cannot drain the credit that the CI review jobs use. The jobs fail closed when the secret is missing.
5. **Budget enforced before submission.** Token counting is itself an outbound request (`POST /v1/messages/count_tokens`) that carries the prompt, so it runs only on the exact payload that already passed condition 1, under the same dedicated key. The job counts tokens for every request and refuses to submit the batch when the worst-case cost (input plus `max_tokens` output at batch rates, from a config file with a `price_review_by` date) exceeds the configured ceiling. A run after `price_review_by` exits non-zero until the prices are re-reviewed, so stale prices fail closed like a missing secret. Actual usage is summed after collection and written to the job summary.
6. **No silent success.** Zero modules, a batch that is not `ended`, any errored, expired or cancelled request, a missing or duplicated `custom_id`, a `stop_reason` other than `end_turn`, output that fails the JSON schema, or a failed batch delete (condition 8) each exit non-zero with a distinct message. The collect job is never `continue-on-error`. A canary is in every batch: a fixed synthetic request built by the submitter from a fixture with a known unwired defect, not a repository module, and excluded from the golden-list comparison in condition 1. If the canary finding is absent, the run fails and files nothing.
7. **Model output is data.** Findings are validated against a strict JSON schema with enumerated `kind` and `severity`, truncated and escaped before filing, and posted through the REST API from validated fields. The first run, and any run until the owner flips `card_mode` to `cards`, files one summary issue rather than per-finding cards. Cards per run are capped.
8. **Retention.** Once a batch id exists, the batch is deleted through the API on every exit path of the collect job, whether collection succeeded or failed (an `if: always()` step or a `finally`), so repository-derived prompts do not sit in the vendor's 29-day result retention. A batch that never reaches `ended` is cancelled, then polled until `processing_status` is `ended` (bounded by a configured cancel timeout), then deleted; if that timeout expires, the run exits non-zero with its own message and records the batch id so it can be deleted later. A failed or non-2xx delete makes the run exit non-zero with its own message. GitHub artifacts carrying the batch id and cost carry no headers or secrets and use the repository's default retention.
9. **Not in the application.** The client is the standard library (`urllib`); no SDK is added to any `requirements*.txt`, and nothing the audit installs is imported by the backend or the UI.

## Consequences

- The audit's model and API stay without an IRP grade-A entry. The #224 implementation PR must add the LIB-STACK row under CI tooling (next to the ADR 0001 row), extend the S1 `scope:` line to cite both ADRs, and add this ADR to the `.claude/CLAUDE.md` hard-requirements note; the exemption is not in force for a run until those exist.
- The product's bar is unchanged. Nothing on the runtime or data path is touched by this decision.
- Both repositories are public, so run logs, artifacts and the issues the audit files are world-readable. Conditions 1, 6 and 7 are what keep that acceptable; the Context section records why.
- Changing any condition (walking the filesystem, moving to the self-hosted runner, widening permissions, sharing the review key, dropping the budget check, letting a run succeed on nothing, filing unvalidated output) needs a new ADR that supersedes this one.
- After the monorepo merge (D9, #125) this ADR and ADR-016 collapse into one; until then both are required.
- Known drive-bys recorded by the design gate, tracked separately: `ci.yml` pins `checkout` and `setup-python` by tag; `scripts/testing/tests/` is run by no workflow.
